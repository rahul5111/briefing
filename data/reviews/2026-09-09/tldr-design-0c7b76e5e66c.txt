═══ 01_DRAFT ═══

Cursor has released new capabilities allowing teams to run its AI-powered Cloud Agents on dynamically scheduled pools of machines within their own networks, rather than exclusively on Cursor-hosted virtual machines. Cursor states that cloud agents currently create more than 60 percent of the pull requests it merges internally, and the feature addresses the growing need for enterprises to control where agents execute and what infrastructure they use. 

Under the self-hosted setup, the agent loop, inference, and planning remain in the Cursor cloud, while tool execution moves to machines managed by the user, such as laptops, virtual machines, or infrastructure provided by partners including AWS Lambda, Cloudflare, Coder, Daytona, E2B, Modal, Namespace, and Vercel. To register a machine, users install the Cursor CLI and run the agent worker start command, establishing a long-lived outbound HTTPS connection to the Cursor cloud. Cursor never initiates a connection into the user network.

The system supports individual personal workflows through My Machines and scaled enterprise needs through Pools, which are named queues of workers. A controller watches the request queue and uses a team-supplied spawn script to automatically start machines as demand rises and disconnects them when idle. To manage costs and startup times, teams can configure idle timeouts and hibernation features that snapshot and stop idle machines, allowing them to restore with full state if a follow-up arrives. 

Additionally, the update expands computer use capabilities to Linux workers alongside Macs, enabling agents to click, take screenshots, and control browsers, while integrations like Namespace Devboxes provide real Macs running on Apple silicon for iOS development. Cursor-hosted environments remain the default option, providing dedicated VMs with per-agent isolation, secret redaction, egress controls, and signed commits.
